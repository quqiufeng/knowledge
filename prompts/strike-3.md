【第三弹：上线迁移、规范元数据校验与 Agent 报错闭环】

结合上述上下文，请针对以下 3 个关键工程卡点给出架构级与代码级深度解法：

## 1.（架构平滑迁移与数据对账）双跑 Diff 与切换策略

原先有一套轻量级本地存储（mmap/KV Cache：250 万条目 + 调用图 + 768 维向量 HNSW 文件），现需无缝迁移到本 PostgreSQL + JSE 本体系统，上层 AI Agent 不得中断。

- 生产环境如何设计"双跑（Shadow Dual-Run）+ 差异对比（Diff）"机制，以低延迟校验 JSE 编译产物在旧引擎与 PG 引擎下的结果一致性？4 类核心查询（精确 key 读取、符号查询、上下文图展开、语义搜索）各自的 diff 策略与容差（语义搜索 Top-K 顺序差异是否可接受）如何定？
- 灰度切流与数据追平（Reconciliation）的最佳实践：先读流量灰度还是先数据对账？切换的 Go/No-Go 判定标准是什么？
- 迁移期间旧 mmap 系统仍在写入（索引管线串行产出），PG 侧增量追平如何实现？

## 2.（Schema-as-Data 与动态校验）规范条目的版本化与校验复用

Knowledge 倡导"规范也是数据"：用特定的 knowledge 规范条目定义某类 Chunk 或业务对象的必填字段与属性约束（如 `meta.category = "chunk"` 的条目必须含 `kind/lang/file/symbol`）。

- 这套规范用 JSON Schema 表达，还是设计为自定义的 JSE 范式？应用层的写入校验引擎如何与 JSE 查询编译器共享同一套 AST/路径白名单机制（避免两套解析代码漂移）？
- 规范条目自身变更（升级到 v2 规范）时：旧数据按旧规范校验还是新规范？生效期与 version 乐观锁如何防止"规范更新 vs 数据写入"的竞态？
- 校验失败的报错如何统一进入第 3 问的 LLM 错误载荷？

## 3.（LLM 友好报错与自我修正）结构化 Error Payload 设计

当 LLM 生成了非法的 JSE 表达式（路径写错、算子拼错、违反数据规范）时，语法/语义/规范三层校验器必须拦截并回传报错。

- 请提供一套 LLM-Friendly Error Standard 结构化报错 Payload 模板（含错误码、表达式树中的定位路径、违规规则、最小修复示例），使 LLM 单次 Retry（Self-Correction）修正 JSE 的成功率最高。
- 请区分三类错误的载荷设计：① 语法/算子未知（编译器层）；② 路径不在白名单（安全层）；③ 违反规范条目（数据层）。
- 请配套给出 System Prompt 引导片段（如何向 LLM 描述 JSE 算子目录与报错回传协议），并讨论：算子目录全量塞 prompt 的 token 膨胀问题，是分层加载（先目录后细节）还是一次给全？
